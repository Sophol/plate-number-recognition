CAMBODIAN LICENSE PLATE RECOGNITION (ANPR) — PYTHON PLAN

============================================================
Stack: Python 3.11/3.12 + PostgreSQL | Cameras: IP/CCTV via RTSP

WHY A CUSTOM PIPELINE
Cambodian plates contain Khmer province name (top), Latin/digits (middle),
and English province name (bottom).
Common layouts include Type 1 / Type 2 for private vehicles.
Generic ANPR APIs may recognize the Latin/digit line but can be unreliable
for Khmer province recognition and Cambodian plate-type classification.
A Cambodian-specific pipeline allows dedicated detection, province
classification, OCR, validation, and frame voting.
RECOGNITION PIPELINE

Step 1. Plate detection
- YOLOv8/YOLOv11 segmentation fine-tuned on Cambodian plates.
- Detects plate location and optionally plate type
(Type 1 / Type 2 / government / NGO / commercial etc.).

Step 2. Perspective correction
- Use segmentation mask to determine plate corners.
- Apply OpenCV homography/perspective warp.
- Normalize the plate before OCR.

Step 3. Text zone split
- Crop top zone: Khmer province name.
- Crop middle zone: Latin letters + digits.
- Crop bottom zone: English province name.

Step 4. Character/province recognition
- Middle zone: PaddleOCR for Latin letters and digits.
- Top zone: use a small image classifier for Cambodian provinces
instead of relying on Khmer OCR.
- Bottom zone: optional English OCR as a cross-check.

Step 5. Cross-frame tracking
- Track each detected plate/vehicle across consecutive frames
(IoU tracker or ByteTrack keyed off the YOLO detections) before
voting, so votes are only taken across frames confirmed to be
the same physical vehicle.
- Assign a track_id per vehicle transit; close the track after a
gap timeout or when the vehicle leaves the ROI.
- This also gives natural dedup/cooldown boundaries per vehicle.

Step 6. Validation & voting
- Validate plate format with regex and position rules, selected by
plate-type (see RECOGNITION VALIDATION).
- Province classifier should agree with English OCR when available.
- Vote across 3-5 consecutive frames within the same track_id before
committing a result.
- Store confidence scores for detector, OCR, and province classifier.

Step 7. Model export
- Export trained models to ONNX.
- Production inference can use ONNX Runtime GPU or TensorRT.
- Python is used for training, inference, API, and workers.

HARDWARE

Central server:
- NVIDIA GPU
- 16-32 GB RAM
- NVMe SSD
- Gigabit/10GbE networking

Possible GPUs:
- NVIDIA T4
- NVIDIA L4
- RTX 4060 or better

Edge:
- NVIDIA Jetson Orin Nano
- NVIDIA Jetson Orin NX

Camera:
- 1080p minimum
- Mount at <=30 degrees to plate direction where possible
- IR illumination for night
- Fast shutter for moving vehicles
- Correct exposure and focus

Camera positioning remains one of the most important factors in ANPR
accuracy.

Clock sync:
- All camera hosts, edge devices, and the central server must run
NTP and stay synced to the same time source.
- frame_ts is used for cross-camera tracking, gate event ordering,
and monthly partitioning; clock drift silently corrupts all three.

PERFORMANCE STRATEGY
Sample cameras at approximately 5-10 FPS.
Use lane/ROI filtering before expensive inference.
Use motion detection to avoid processing completely static scenes.
Use tracking/frame voting to reduce duplicate recognition.
Batch inference when appropriate for multi-camera servers.
Use a bounded frame queue between camera worker and inference worker;
under GPU overload, drop the oldest queued frame rather than blocking
the camera worker or dropping the newest frame.
Benchmark:
PyTorch
ONNX Runtime GPU
TensorRT
before selecting the production runtime.
RECOGNITION VALIDATION

Plate format is selected by the plate-type classifier output from
Step 1 (detection). Do not apply one regex to every plate.

Type              Example      Regex
----------------- ------------ --------------------------------
Private car       2D-0888      ^[1-9][A-Z]{1,2}-\d{4}$
Motorcycle        1KH-2233     ^[1-9][A-Z]{2}-\d{4}$  (verify against
                                actual motorcycle plate samples)
Government        (TBD)        Define after collecting samples;
                                often has distinct prefix/color
Commercial        (TBD)        Define after collecting samples
NGO                (TBD)       Define after collecting samples
Diplomatic/other  (TBD)        Define after collecting samples

Treat every "(TBD)" regex as a Phase 0/1 deliverable: collect at
least a handful of real samples per plate type before writing the
rule, rather than guessing the format up front.

Adjust validation rules for:
- Government plates
- Commercial plates
- NGO plates
- Motorcycle plates
- Other special Cambodian plate formats

Use position-aware character correction for common OCR errors:

O <-> 0
I <-> 1
B <-> 8


Do not blindly replace characters; apply corrections according to the
expected character position.

Example:

Frame 101 -> 2D-0888
Frame 102 -> 2D-0888
Frame 103 -> 2D-088B
Frame 104 -> 2D-0888
Frame 105 -> 2D-0888


Final result:

2D-0888

MODEL PROMOTION

A new model version must not go straight to controlling gates.

1. Train and evaluate offline against the held-out test set.
   Require it to beat the current production model on the primary
   KPI (full plate exact-match accuracy) before proceeding.
2. Shadow-score: run the candidate model_version alongside the
   production model on the same live frames for a defined window
   (e.g. 1-2 weeks or N thousand reads), writing candidate results
   to plate_reads without acting on them (no gate/alert triggers).
3. Compare candidate vs. production accuracy on the same frames,
   including per-province and per-plate-type breakdowns, not just
   the aggregate.
4. Promote by flipping which model_version the inference worker
   acts on; keep the previous version's weights and code path
   available for immediate rollback.
5. Define an explicit rollback trigger (e.g. exact-match accuracy
   drop of more than X% over Y reads) and who is authorized to
   pull the trigger.

SECURITY

Because this system can trigger physical gate actions and stores
per-vehicle tracking data, treat it as security-sensitive, not just
another internal dashboard.

- Authentication required on FastAPI for all non-public routes;
  no anonymous access to plate_reads, vehicles, or gate control.
- Role-based authorization: separate roles for read-only viewers,
  list (whitelist/blacklist) editors, and gate-override operators.
  Editing vehicles/list_type should require a higher privilege than
  viewing plate_reads.
- Audit every whitelist/blacklist edit and every manual gate action
  with actor, timestamp, and reason — gate_events.actor is a start,
  but list edits need the same treatment (consider a generic
  audit_log table rather than overloading gate_events).
- Rate-limit and authenticate any externally reachable API surface;
  RTSP credentials and camera network should stay on an isolated
  VLAN, not exposed alongside the public-facing API.
- Encrypt plate_reads/vehicles data at rest if required by local
  data protection rules, and restrict MinIO/S3 bucket access to
  backend services only (no public bucket policies).

RISKS & MITIGATIONS

Night glare / dirty plates
-> IR camera, correct exposure, image preprocessing, retraining.

Motorbike plates
-> Separate class/detector strategy, higher sampling rate on
motorcycle lanes.

Similar characters
-> Position-aware validation + temporal frame voting.

Khmer recognition
-> Province image classifier instead of primary Khmer OCR.

Different plate layouts
-> Plate-type classification + layout-specific processing.

Camera angle
-> Correct installation and perspective correction.

Model drift
-> Continuously collect production misreads and retrain.

Network/RTSP failure
-> Automatic reconnect and local buffering.

GPU overload
-> ROI filtering, motion gating, tracking, optimized ONNX/TensorRT
inference, bounded drop-oldest frame queue between camera and
inference workers.

Duplicate reads
-> Tracking (ByteTrack/IoU) + temporal grouping + cooldown per
vehicle, keyed off track_id rather than time window alone.

Clock drift across cameras
-> NTP on all camera/edge hosts; alert if a camera's reported
frame_ts skews from server time beyond a threshold.

Unauthorized gate/list access
-> Authentication + role-based permissions on all API routes,
audit logging on every list edit and gate override.

Bad model promoted to production
-> Shadow-score new model_version against production on live
traffic before cutover; defined rollback trigger and process.
